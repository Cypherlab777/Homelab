# 🔧 Troubleshooting — IPv6 on pfSense

## TL;DR

- **Goal:** Enable IPv6 on pfSense (DHCPv6 Prefix Delegation from VOO) and provide SLAAC on VLAN 10 (Family).
- **Issue 1 — Delegated prefix not visible:** The WAN had a `/128` GUA, but no prefix was visible in the logs. DHCPv6 debug logs showed that VOO delegates only a `/64` (IA_PD).
- **Issue 2 — No GUA on VLAN 10:** `dhcp6c.conf` requested a `/56` (`sla-len 8`) while VOO delegated a `/64`. Restoring the `/64` request (`sla-len 0`) and renegotiating fixed it. The mismatch is a probable cause, not a confirmed one.
- **Issue 3 — Hosts without an IPv6 address:** Router Advertisements were not enabled on the FAMILY interface. Enabling them (Unmanaged mode, RDNSS) restored SLAAC.
- **Status:** All three issues resolved. Next: continue testing IPv6 (DNS resolution, firewall rules, network isolation).

## Introduction

While deploying IPv6 on my homelab, I encountered several issues with DHCPv6 Prefix Delegation, Track Interface and SLAAC.

My goal was to enable IPv6 on my pfSense WAN interface and then use the prefix delegated by VOO on VLAN 10 (Family).

Although the initial configuration seemed relatively straightforward, I encountered three problems:

1. I couldn't find the IPv6 prefix delegated by VOO.
2. Track Interface was configured, but VLAN 10 was not receiving any Global Unicast Address.
3. pfSense had a GUA on the FAMILY interface, but the end hosts were not receiving IPv6 addresses through SLAAC.

Below are the investigations and corrections I performed.

## 1. Unable to Find the Prefix Delegation

### Problem

After enabling DHCPv6 on my WAN interface, pfSense successfully obtained an IPv6 Global Unicast Address with a `/128` prefix length.

However, I couldn't find which IPv6 prefix VOO had delegated to my router.

This was important because I needed to know the prefix size to determine how many `/64` subnets I could use for my VLANs.

### Investigation

With the help of AI, I started by checking the DHCPv6 logs in pfSense.

Under:

**Status → System Logs → DHCP**

I searched for messages containing:

```text
dhcp6c
IA_PD
prefix
NoPrefixAvail
```

I could see DHCPv6 messages, but I couldn't find any clear information about Prefix Delegation.

This did not necessarily mean that VOO had refused the delegation. I simply didn't have enough information to confirm it.

### Action Taken

I temporarily enabled DHCPv6 debug mode:

**Start DHCP6 client in debug mode**

I then restarted the DHCPv6 negotiation on the WAN interface to generate more detailed logs.

### Result

This time, I found an IA_PD entry in the logs:

```text
IA_PD prefix: 2001:db8:106:2ee0::/64
```

VOO was successfully delegating an IPv6 prefix, but only a `/64`.

This gave me one public `/64` subnet that I could use for an internal network with SLAAC.

### What I Learned

Having a GUA on the WAN interface does not automatically prove that an IPv6 Prefix Delegation has been received.

It is important to distinguish:

- **IA_NA:** Requests IPv6 addresses.
- **IA_PD:** Requests IPv6 prefixes.

DHCPv6 debug logs can be useful for identifying the information actually returned by the ISP.

## 2. Track Interface Not Assigning a GUA to VLAN 10

### Problem

After identifying my delegated `/64`, I decided to use it on VLAN 10.

Under **Interfaces → FAMILY**, I configured:

| Setting | Value |
|---|---|
| IPv6 Configuration Type | Track Interface |
| IPv6 Interface | WAN |
| IPv6 Prefix ID | 0 |

However, no IPv6 Global Unicast Address appeared on the FAMILY interface.

Under **Status → Interfaces → FAMILY**, only a link-local address was present:

```text
fe80::1
```

At the same time, the DHCPv6 logs confirmed that VOO was delegating a `/64`.

### Attempt to Obtain a /56

Before resolving this issue, I had also tried requesting a larger delegated prefix from VOO.

Under **Interfaces → WAN → DHCP6 Client Configuration**, I configured:

```text
DHCPv6 Prefix Delegation Size : 56
Send IPv6 Prefix Hint : Enabled
```

Prefix Hint allows the DHCPv6 client to indicate the preferred delegated prefix size.

However, after applying the changes and checking the logs, VOO was still delegating a `/64`.

Example:

```text
IA_PD prefix: 2001:db8:104:22e::/64
```

VOO had not granted the requested `/56`.

I decided not to investigate this further for the moment and continued with the available `/64`.

### Investigating Track Interface

Even though Track Interface appeared to be correctly configured, FAMILY was still not receiving any GUA.

AI suggested checking the DHCPv6 client configuration file generated by pfSense.

Under **Diagnostics → Command Prompt**, I ran:

```bash
cat /var/etc/dhcp6c.conf
```

I found the following configuration:

```text
id-assoc pd 0 {
    prefix ::/56 infinity;
    prefix-interface lagg0.10 {
        sla-id 0;
        sla-len 8;
    };
};
```

### Analysis

Three parameters caught my attention.

**`prefix ::/56 infinity;`**

The DHCPv6 client configuration contained a requested prefix size of `/56`.

**`sla-id 0;`**

This identifies the subnet selected for the interface.

In my case, it corresponded to Prefix ID `0`.

**`sla-len 8;`**

This specifies 8 additional bits for subnet identification.

The calculation was:

```text
56 + 8 = 64
```

pfSense was preparing to divide a `/56` into `/64` subnets.

However, VOO had actually delegated a `/64`.

There was therefore a mismatch between the configured DHCPv6 request and the prefix that had been received.

This was a possible explanation for why VLAN 10 was not receiving its GUA.

### Correction

I decided to restore the original WAN settings:

```text
DHCPv6 Prefix Delegation Size : 64
Send IPv6 Prefix Hint : Disabled
```

After applying the changes, I checked the configuration file again:

```bash
cat /var/etc/dhcp6c.conf
```

It now contained:

```text
id-assoc pd 0 {
    prefix-interface lagg0.10 {
        sla-id 0;
        sla-len 0;
    };
};
```

This time, `sla-len` had changed from `8` to `0`.

No additional subnet bits were needed to use a `/64` from a delegated `/64`.

### Result

After this correction and another DHCPv6 negotiation, the FAMILY interface finally obtained an IPv6 Global Unicast Address.

Example observed (IPv6 address anonymized):

```text
Interface : lagg0.10

IPv6 Address :
2001:db8:106:3e2a::1/64
```

The issue was resolved.

### Possible Root Cause

The mismatch between the requested `/56` and the delegated `/64` is a possible explanation for the issue.

However, I cannot confirm that this was the only cause.

Changing the configuration also triggered another DHCPv6 negotiation, which may have contributed to restoring the IPv6 prefix assignment.

### What I Learned

- Prefix Hint is a request, not a guarantee.
- Track Interface depends on the IPv6 prefix actually delegated by the ISP.
- The `dhcp6c.conf` file can help understand how pfSense prepares its DHCPv6 requests and prefix assignments.
- The `sla-len` parameter is related to subnet identification within a delegated prefix.
- The `dhcp6c.conf` file should not be edited directly because it is automatically generated by pfSense.

## 3. SLAAC Not Working on the Family Network

### Problem

After resolving the Track Interface issue, the FAMILY interface correctly had an IPv6 Global Unicast Address.

The next step was to allow the end hosts on my family network to automatically configure their IPv6 addresses using SLAAC.

However, when I checked the IPv6 configuration of a Windows host using:

```powershell
ipconfig /all
```

I couldn't find any IPv6 Global Unicast Address.

The host only had a link-local address:

```text
fe80::2%16
```

IPv4 was working correctly, but IPv6 autoconfiguration was not.

### Investigation

I first verified that the FAMILY interface on pfSense had a valid IPv6 Global Unicast Address.

This was confirmed.

The problem therefore no longer appeared to be related to Prefix Delegation or Track Interface.

I then checked the **Router Advertisements (RA)** configuration under:

**Services → Router Advertisement → FAMILY**

I discovered that Router Advertisements were not enabled on this interface.

### Explanation

This helped me better understand the difference between Track Interface and SLAAC.

Track Interface allows pfSense to assign the delegated IPv6 prefix to VLAN 10.

However, the end hosts also need to receive Router Advertisements to automatically configure their IPv6 addresses through SLAAC.

Router Advertisements provide information such as:

- The available IPv6 prefix.
- The prefix length.
- Information required for address autoconfiguration.
- The IPv6 default router.

Without these advertisements, the end hosts did not receive the information needed to generate their GUAs through SLAAC.

### Correction

Under **Services → Router Advertisement → FAMILY**, I configured:

| Setting | Value |
|---|---|
| Router Mode | Unmanaged |
| Router Priority | Normal |
| PREF64 | Disabled |

Unmanaged mode allows end hosts to automatically configure their IPv6 addresses using SLAAC.

I also enabled DNS server advertisement through Router Advertisements.

I chose public IPv6 DNS servers from Cloudflare and Google:

```text
Cloudflare : 2606:4700:4700::1111
Google     : 2001:4860:4860::8888
```

DNS information is advertised using RDNSS, which allows IPv6 hosts to discover DNS servers without using DHCPv6 for DNS configuration.

I haven't studied the pfSense DNS Resolver configuration in detail yet, so I decided to use public DNS servers for now.

### Result

After applying this configuration, the end hosts on VLAN 10 were able to obtain their IPv6 Global Unicast Addresses through SLAAC.

The issue was therefore caused by Router Advertisements not being enabled on the FAMILY interface.

### What I Learned

- Track Interface alone does not enable SLAAC for end hosts.
- Router Advertisements must be enabled on the relevant VLAN.
- SLAAC allows hosts to generate their own IPv6 addresses.
- Router Advertisements also allow hosts to discover the IPv6 default router.
- RDNSS allows DNS servers to be advertised through RA messages.
- Having only a link-local address does not mean that a host has IPv6 Internet connectivity.

## 5. Conclusion

This troubleshooting helped me better understand how IPv6 works on pfSense.

At first, I thought that obtaining a WAN IPv6 address and enabling Track Interface would be enough to automatically configure IPv6 on VLAN 10.

I eventually understood that several mechanisms were involved:

```text
1. DHCPv6 IA_NA
   → Obtain a WAN IPv6 address

2. DHCPv6 IA_PD
   → Obtain the delegated prefix from VOO

3. Track Interface
   → Assign the delegated prefix to VLAN 10

4. Router Advertisements
   → Advertise the prefix and default router to hosts

5. SLAAC
   → Automatically configure IPv6 addresses on end hosts
```

I also learned how useful DHCPv6 logs and pfSense-generated configuration files can be when troubleshooting network issues.

This experience helped me move from a mainly theoretical understanding of DHCPv6 and SLAAC to a working IPv6 configuration on my family network.

My next step will be to continue testing IPv6, especially DNS resolution, firewall rules and network isolation, before starting my future IPv6 routing labs on my Cisco switches.
